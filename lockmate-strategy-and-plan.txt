# 1. Executive Strategy

LOCKMATE is a healthcare data privacy firewall designed to remove patient identities from fragmented hospital records while preserving clinically meaningful information.

The system must solve three connected problems:

1. **Identity detection:** Find direct and indirect identifiers across structured and unstructured healthcare data.
2. **Identity resolution:** Recognize the same patient across hospitals, scripts, spelling variations, and different record formats without incorrectly merging different patients.
3. **Privacy preservation:** Protect against re-identification attacks while retaining clinical utility.

The central strategy is:

> Remove identities. Preserve medicine. Defeat linkage attacks.

The competition must be approached as an engineering and evaluation problem, not merely an NLP or anonymization problem.

A large system that produces invalid output, loses clinical data, or leaks identifiers will perform worse than a smaller system that reliably satisfies the organizer's contract.

## Three flagship differentiators

| Differentiator | Engineering objective |
|---|---|
| Cross-Script Identity Intelligence | Link patient records across English, Hindi, Hinglish, and transliterated names |
| Clinical Integrity Protection | Preserve medicines, dosages, diagnoses, laboratory values, and clinically important measurements |
| Attacker-Aware Privacy Shield | Measure and reduce re-identification risk using realistic quasi-identifier attacks |

These capabilities must be demonstrated through actual pipeline execution and reproducible evaluation.

# 2. Organizer Compatibility: Mandatory Corrections

The following changes are required to make the original strategy compatible with the hackathon.

| Original proposal | Revised implementation decision |
|---|---|
| HIPAA Safe Harbor as the main privacy framework | Use the organizer's exact Indian healthcare and synthetic-data requirements as the implementation authority. HIPAA can be background reference only. |
| Quarantine all files as an initial implementation | Use quarantine only for unsafe or unsupported files. Build a working sanitization path. Quarantine-all is not a viable submission strategy. |
| Medical whitelist | Use contextual medical protection, not an unconditional exemption from PII detection. |
| Document-level name replacement | Use role-aware mention resolution to distinguish patients, relatives, doctors, and other people. |
| Transitive graph-based linkage | Use conservative pairwise matching, cannot-link constraints, and cluster consistency checks. |
| Latin-1 as a general fallback | Do not treat arbitrary Latin-1 decoding as evidence that a file is valid text. |
| Plain-text treatment for every decodable unknown format | Unknown or unsupported formats must be quarantined unless a validated parser exists. |
| k-anonymity as proof of anonymity | Use it as one diagnostic measure alongside attacker simulation and utility measurements. |
| Byte-identical reports on repeated runs | Make sanitized content and deterministic fields stable. Keep runtime and memory telemetry truthful. |
| AES-GCM for every intermediate | Minimize raw disk intermediates first. Encrypt required intermediates only with correct key and nonce management. |
| CRF as an automatic requirement | Establish a strong rule-based baseline first. Add a CRF only if data, time, and measured improvement justify it. |
| Assume official validator and practice data are present | Inspect the actual workspace and obtain official assets before claiming availability. |

**Important:** The official contract overrides every implementation preference in this document.

# 3. Exact Organizer Contract

This section is non-negotiable.

## 3.1 Execution environment

The solution must run:

- Offline.
- On CPU only.
- With a maximum of 2 CPUs.
- Within 4 GB RAM.
- Within 15 minutes.
- Without network access during execution.

## 3.2 AI/ML restrictions

Do not use:

- Hosted LLMs in the submitted application.
- Local LLMs.
- Distilled LLMs.
- Generative models.
- Pretrained transformers larger than 50 million parameters.

Permitted approaches include rules, gazetteers, classical ML, CRFs, and small self-trained models where compliant.

Every model used must be declared in the README.

## 3.3 Configuration

Required file: `raksha.toml`

```toml
[submission]
name = "your-team-name"
setup = "pip install -r requirements.txt"
run = "python main.py --input {input} --output {output}"
```

Required environment variable:

```text
RAKSHA_SECRET
```

Never change these official identifiers to match LOCKMATE branding.

Never hardcode, print, log, or write the secret to disk.

## 3.4 CLI

```bash
python main.py --input <input_directory> --output <output_directory>
```

## 3.5 Required output

```text
output/
├── sanitized/
├── report.json
└── records.jsonl
```

### Sanitized files

- Preserve directory structure where appropriate.
- Preserve supported file formats.
- CSV and TSV remain CSV and TSV.
- JSON remains JSON.
- FHIR output remains valid R4.
- Use UTF-8.
- Rename PII-bearing filenames.
- Never copy raw files as sanitized.
- Quarantine files that cannot be safely processed.

### report.json

Each input file must have an entry identified by its SHA-256 hash, not its original filename.

Include:

- Output path or null.
- Sanitized or quarantined status.
- Quarantine reason when applicable.
- Accurate totals.
- Processing duration.
- Peak memory usage.

Required totals:

- `files_total`
- `files_sanitized`
- `files_quarantined`
- `records_processed`
- `identifiers_detected`
- `records_linked`
- `records_generalized`
- `records_suppressed`
- `records_quarantined`

Do not invent metrics or expose original filenames.

### records.jsonl

One line per patient record.

Required information:

- `file`: sanitized file path.
- `loc`: record location.
- `patient`: pseudonym or null.

Location conventions:

- CSV row: `row:N`, with first data row `row:0`.
- JSON: JSON pointer.
- Text/FHIR: `doc`.

The same patient must have the same pseudonym across all files.

The pseudonym must also appear inside the corresponding sanitized record.

If identity is uncertain, use null.

### Supported initial formats

- TSV.
- JSON.
- Plain text.

### Extended formats

- FHIR R4.
- Nested JSON.
- Metadata.

### Implementation

- File discovery.

- Delimiter detection.
- Column classification.
- Structural validation.
- Safe parser errors.
- Path traversal protection.
- Symlink handling.
- Resource limits.

### Encoding correction

Try reliable encoding detection and explicitly supported encodings.

Do not use Latin-1 as an unrestricted fallback that converts arbitrary binary into apparent text.

### Acceptance criteria

- Supported files parse correctly.
- Original input remains unchanged.
- Malformed files are quarantined safely.
- No raw file is silently copied into sanitized output.
- File identity and record locations remain traceable.

## Stage 2 — Unified Record Model

**Priority: P0**

Build a common internal representation for all supported formats.

It should retain:

- Source file hash.
- Source format.
- Record location.
- Original structural location.
- Field values.
- Field types.
- Original and normalized text.
- Span-offset mappings.
- Processing status.

The unified representation must preserve enough structural information to serialize the sanitized output back into the original format.

Do not flatten all records into unstructured text. That would make reliable reconstruction and FHIR preservation difficult.

**Acceptance:** CSV, JSON, and text inputs can use the same detection and privacy pipeline without losing their output structure.

## Stage 3 — Multilingual PII Detection

**Priority: P0**

Implement layered detection.

### 3.1 Unicode normalization

- NFC normalization.
- Zero-width character handling.
- Devanagari digit normalization.
- Whitespace normalization.
- Relevant script normalization.
- Bidi and confusable-character checks.

Maintain offset mappings so normalized spans can be safely transformed in the original representation.

### 3.2 Structured detection

Inspect:

- Headers.
- JSON keys.
- Nested fields.
- Field values.
- Filename components.
- Metadata.
- FHIR references and extensions.

Do not trust headers alone.

### 3.3 Direct identifiers

Detect contextually:

- Phone numbers.
- Email addresses.
- Aadhaar-like identifiers.
- ABHA identifiers.
- PAN.
- UHID/MRN.
- Insurance identifiers.
- Personal addresses.
- Patient names.
- Relative names.

Use established libraries where appropriate.

Validate identifier formats and checksums against authoritative specifications before implementing them.

A numeric pattern alone does not establish identity.

### 3.4 Name detection

Combine:

- Honorifics.
- Relationship markers.
- Gazetteers.
- Transliteration.
- Contextual rules.
- Optional classical ML.

Examples:

| Input | Expected handling |
|---|---|
| Dr. Ramesh | Preserve doctor identity where required |
| C/O Ramesh | Detect possible relative name |
| C/O fever | Preserve clinical phrase |
| S/o Rajan | Detect relative identity |
| Parkinson's disease | Preserve diagnosis |
| Dolo 650 BD | Preserve medication and dosage |
| मोहम्मद आरफ | Recognize possible patient name |

Do not blindly redact every occurrence of a detected name.

Use role-aware classification.

## Stage 4 — Clinical Integrity Protection

**Priority: P0**

Clinical preservation is as important as PII removal.

Protect:

- Drug names.
- Drug strengths.
- Dosages.
- Frequencies.
- Medication durations.
- Laboratory names.
- Units.
- Vitals.
- Diagnoses.
- Procedures.
- Clinically meaningful stay durations.

The medical layer is a contextual safeguard, not an unconditional whitelist.

For example:

- Preserve `Dolo 650 BD`.
- Preserve `5 mg`.
- Preserve `Parkinson's disease`.
- Detect and redact an actual patient name even if it occurs in a clinical sentence.

Implement span-level protection rather than excluding entire sentences from scanning.

**Acceptance:** Tests demonstrate that personal identifiers are removed while clinical values remain intact.

## Stage 5 — Patient Identity Resolution

**Priority: P1**

This is a flagship differentiator.

### Candidate generation

Use blocking based on suitable signals:

- Normalized names.
- Transliteration.
- Phonetic similarity.
- Shared identifiers.
- Relative-name evidence.
- Other contextual attributes.

### Pairwise scoring

Use weighted evidence:

- Name similarity.
- Token similarity.
- Transliteration similarity.
- Shared identifiers.
- Relative-name agreement.
- Age plausibility.
- Geographic consistency.
- Date consistency.

A Fellegi–Sunter-style model is an option, not a mandatory implementation.

### False-merge prevention

Implement:

- Pairwise thresholds.
- Cannot-link constraints.
- Conflicting-identifier checks.
- Cluster consistency.
- Conservative decisions.

Never automatically merge connected components based only on transitive similarity.

If identity is uncertain, return null.

**Acceptance:** Linkage precision, recall, and false-merge rate are measured on synthetic labelled fixtures.

## Stage 6 — Stable Pseudonymization

**Priority: P1**

Use HMAC-SHA256 through a vetted cryptographic library.

Conceptual approach:

```text
pseudonym = HMAC-SHA256(
    RAKSHA_SECRET,
    canonical_patient_identity
)
```

The actual implementation must define:

- Canonical identity.
- Encoding.
- Output representation.
- Collision considerations.
- Secret handling.
- Key separation, if required.

Requirements:

- Same patient and secret produce the same pseudonym.
- Different secret produces a different pseudonym.
- Pseudonyms are stable across hospitals.
- Pseudonyms are not reversible.
- Uncertain identities receive null.

Do not create custom cryptographic algorithms.

## Stage 7 — Privacy Shield

**Priority: P1**

### 7.1 Date shifting

Use a deterministic patient-specific date shift derived from the secret.

Requirements:

- Consistent shift across a patient's records.
- Preserve intervals.
- Preserve chronological ordering.
- Handle date-only and timezone-aware values correctly.
- Do not modify unrelated numbers or medication durations.
- Different secrets produce different transformations.

### 7.2 Age generalization

Use configurable age bands.

Handle:

- Infants.
- Boundary values.
- Unknown age.
- Invalid age.
- Very high age values.

Do not invent an age when none exists.

### 7.3 Location generalization

Possible transformations:

- Village to district.
- District to state.
- PIN code to broader region.
- Suppression of rare location combinations.

### 7.4 Rare-value suppression

Identify combinations of quasi-identifiers that are too unique.

Possible signals:

- Age.
- Village.
- PIN.
- Dates.
- Length of stay.
- Rare diagnosis.

Use k-anonymity as a diagnostic measure, not proof of anonymity.

**Acceptance:** Privacy improvements and utility loss are measured using synthetic data.

# 6. Security Corrections and Implementation Risks

These issues must be explicitly tracked.

| Risk | Required mitigation |
|---|---|
| Latin-1 decodes arbitrary binary | Validate file type and structure independently |
| Medical whitelist hides real names | Contextual, span-level medical protection |
| Document-wide name replacement | Role-aware mention resolution |
| Transitive linkage merges unrelated patients | Pairwise evidence and cannot-link constraints |
| FHIR deep structures leak identity | Traverse references, extensions, contained resources, metadata and attachments |
| Raw temporary files leak PII | Minimize disk intermediates and control temporary storage |
| Incorrect AES-GCM usage | Use vetted APIs and correct key/nonce lifecycle |
| Weak pseudonym canonicalization | Define stable identity canonicalization |
| Unicode offsets corrupt replacements | Maintain normalization-to-original offset mapping |
| k-anonymity damages clinical utility | Measure privacy-utility trade-off |
| CRF consumes time without benefit | Compare against rule-based baseline first |
| Output collisions overwrite files | Deterministic collision-safe naming |
| Partial writes expose unsafe files | Atomic publication |
| Resource exhaustion | File, nesting, decompression and processing limits |
| Report exposes original filename | Hash-based input identity and safe output paths |
